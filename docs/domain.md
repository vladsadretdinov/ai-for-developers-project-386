# Доменная модель и сценарии

Сервис бронирования слотов (упрощённый Calendly). Регистрации и авторизации нет.
Есть две роли: **владелец календаря** (один предзаданный профиль, работает в
админской части) и **гость** (анонимный посетитель, бронирует без аккаунта).

## 1. Доменные сущности

### Владелец (`Owner`)
Единственный заранее заданный профиль. Гость его не создаёт и не редактирует —
наружу доступен только для чтения.

| Поле       | Тип        | Описание                                  |
|------------|------------|-------------------------------------------|
| `id`       | string     | Идентификатор владельца (read-only).      |
| `name`     | string     | Отображаемое имя.                         |
| `email`    | string     | Контактный email.                         |
| `timeZone` | string     | Таймзона IANA, напр. `Europe/Moscow`.     |

### Тип события (`EventType`)
Вид брони, который задаёт владелец. По заданию у типа есть `id`, название,
описание и длительность в минутах.

| Поле              | Тип    | Описание                                 |
|-------------------|--------|------------------------------------------|
| `id`              | string | Идентификатор типа события (read-only).  |
| `title`           | string | Название (1–120 символов).               |
| `description`     | string | Описание (до 2000 символов).             |
| `durationMinutes` | int32  | Длительность встречи (1–1440).           |

### Слот (`Slot`)
Свободный интервал времени, на который можно записаться. **Слоты не хранятся**
как отдельные записи — они вычисляются на лету для конкретного типа события
на ближайшие 14 дней. Слот считается занятым, если на его время уже есть
бронирование (любого типа).

| Поле    | Тип         | Описание                                   |
|---------|-------------|--------------------------------------------|
| `start` | utcDateTime | Начало слота.                              |
| `end`   | utcDateTime | Конец = `start` + `durationMinutes` типа.  |

### Бронирование (`Booking`)
Запись гостя на конкретный слот конкретного типа события. Хранит интервал
времени и контакты гостя. Аккаунт гостя не создаётся.

| Поле          | Тип           | Описание                                          |
|---------------|---------------|---------------------------------------------------|
| `id`          | string        | Идентификатор бронирования (read-only).           |
| `eventTypeId` | string        | Тип события, на который сделана запись.            |
| `start`       | utcDateTime   | Начало встречи.                                   |
| `end`         | utcDateTime   | Конец встречи (read-only, считается сервером).     |
| `guestName`   | string        | Имя гостя (1–120 символов).                        |
| `guestEmail`  | string        | Email гостя.                                       |
| `notes`       | string?       | Необязательный комментарий.                       |
| `status`      | BookingStatus | `confirmed` / `cancelled` (read-only).            |
| `createdAt`   | utcDateTime   | Момент создания (read-only).                       |

## 2. Инварианты домена

1. **Уникальность времени.** На одно и то же время нельзя создать два
   бронирования, даже если это разные типы событий → ответ `409 slot_taken`.
2. **Окно записи 14 дней.** Доступные слоты формируются на 14 дней начиная
   с текущей даты. Запись вне окна невозможна.
3. **Только свободный слот.** Гость может записаться только на слот из списка
   свободных. Время окончания вычисляется сервером по длительности типа.

## 3. Публичный сценарий гостя

1. Открывает страницу видов брони → `GET /public/event-types`
   (название, описание, длительность).
2. Выбирает тип и открывает календарь свободных слотов на 14 дней →
   `GET /public/event-types/{eventTypeId}/slots`.
3. Выбирает свободный слот и создаёт бронирование →
   `POST /public/bookings`.
4. Возможные ответы: `201` — бронирование создано; `409` — время занято или
   вне окна; `404` — тип события не найден; `422` — некорректные данные.

## 4. Сценарий владельца (админская часть)

1. Управляет типами событий: `GET/POST/PUT/DELETE /admin/event-types`.
2. Смотрит страницу предстоящих встреч — все бронирования всех типов в одном
   списке: `GET /admin/bookings`.
3. Может открыть и отменить бронирование:
   `GET/DELETE /admin/bookings/{bookingId}`.

## 5. Задача агенту (формулировка)

> На основе описания домена сформируй TypeSpec-спецификацию, фиксирующую
> HTTP API-контракт сервиса бронирования. Опиши модели `Owner`, `EventType`,
> `Slot`, `Booking` и модели запросов/ошибок. Раздели операции на админскую
> часть владельца (`/admin/*`) и публичную часть гостя (`/public/*`).
> Зафиксируй правило занятости времени через ответ `409`, окно записи 14 дней
> и статусы ответов `201/204/404/409/422`. Спека должна компилироваться
> компилятором TypeSpec и генерировать корректный OpenAPI 3.
