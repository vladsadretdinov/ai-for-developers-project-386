# Пользовательские сценарии (e2e)

Интеграционные проверки выполняются в реальном браузере через Playwright и
прогоняют связку **фронтенд (Angular, :4200)** + **бэкенд (Go, :3001)**.
Фронтенд проксирует `/api` на бэкенд (см. `frontend/proxy.conf.json`).

Бэкенд держит данные **в памяти** и при старте сидит двумя типами событий
(«Демо продукта» — 30 мин, «Консультация» — 60 мин). Слоты вычисляются на лету
на 14 дней (рабочие часы 09:00–17:00 в таймзоне владельца).

## Основной сценарий — бронирование слота (happy path)

Главный путь, который обязаны покрывать тесты.

1. Гость открывает главную страницу `/` и видит список типов встреч.
2. Нажимает «Записаться» у выбранного типа → переходит на `/book/:eventTypeId`.
3. Видит календарь с днями, у которых есть свободные слоты.
4. Выбирает ближайший доступный день.
5. Выбирает свободный слот (время) из списка.
6. Заполняет форму: имя и email (комментарий опционально).
7. Нажимает «Подтвердить».
8. Видит экран подтверждения «Встреча забронирована» с типом, временем и именем гостя.

**Ожидаемый результат:** бронь создаётся (`POST /public/bookings` → `201`),
показывается подтверждение.

## Дополнительные сценарии (граничные случаи)

### A. Слот занят (конфликт, 409)
1. Гость бронирует слот по основному сценарию.
2. Второй гость открывает тот же тип события.
3. Забронированный слот больше не отображается в списке доступных
   (`GET /slots` его не возвращает) — занятость отражается в выдаче.

### B. Валидация формы
1. Гость доходит до формы бронирования и оставляет имя/email пустыми.
2. Нажимает «Подтвердить».
3. Бронь не отправляется, показывается сообщение «Заполните имя и email».

### C. Навигация назад к списку
1. Со страницы бронирования гость возвращается ссылкой «← Все типы встреч».
2. Снова оказывается на списке типов встреч.

## Запуск

```bash
cd e2e
npm install
npx playwright install --with-deps chromium
npm test
```

Playwright сам поднимает бэкенд и фронтенд через `webServer` в
`playwright.config.ts`, поэтому отдельно запускать сервисы не нужно.
